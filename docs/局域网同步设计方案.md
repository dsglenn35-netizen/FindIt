# 「放哪了」局域网双设备同步 · 设计方案

> 版本：v2.1（v2.0 已落地，本文档同步更新至 v2.1 加固项）
> 关联仓库：https://github.com/dsglenn35-netizen/FindIt

---

## 1. 背景与目标

**现状**：v1.1 为单机应用，数据全部存在手机本地（SQLite + `files/photos/`），无网络功能。

**目标**：让**两台 Android 设备在同一个局域网内**同步物品记录、常用位置和照片，实现"家里两台手机 / 手机 + 平板"共用一份数据。

**非目标**（本期不做）：
- 公网/跨网段同步
- 三台以上设备集群
- 云端备份（仍建议用现有"导出备份"功能）

**版本规划**：`versionName = 2.0`，`versionCode = 3`。数据库 v2 → v3 自动迁移，老用户无缝升级，不破坏兼容。

---

## 2. 总体架构（主机-客户端模式）

```
设备 A（主机模式）                   设备 B（客户端模式）
┌─────────────────────────┐  局域网 HTTP   ┌─────────────────────────┐
│ App + 内置轻量 HTTP 服务  │ ◀────────────▶ │ App + 同步客户端          │
│ 监听 0.0.0.0:8888（可改） │    JSON/照片    │ 扫码 / 手动输 IP 连接       │
│ 显示 IP + 二维码 + PIN    │               │ 拉取 + 推送变更            │
└─────────────────────────┘               └─────────────────────────┘
```

**核心原则**：
- 两台设备装的是**同一个 App**，谁都可以开主机模式（能力对等）
- 同步是**双向**的：客户端把自己的变更推给主机，同时拉取主机的变更
- **数据不出局域网**，无需外网、无需账号、无需额外服务器
- 同步**不替代备份**：仍建议定期用"导出备份"存一份 zip

## 3. 数据模型改动（v2 → v3）

### 3.1 items 表

| 新列 | 类型 | 说明 |
|---|---|---|
| `updated_at` | INTEGER | 最后修改时间（毫秒），用于增量同步与冲突裁决 |
| `deleted` | INTEGER DEFAULT 0 | 软删除标记（0/1），同步墓碑 |

**修改入口统一**：所有写操作（新增/编辑/删除）必须同时更新 `updated_at`。

### 3.2 locations 表

新增 `updated_at` 列，以"名称"为同步键（家庭场景数量少，整表合并即可）。

### 3.3 moves 表（移动历史）

**不单独同步**。移动历史作为物品的"子文档"随物品整体传输（见 4.2），避免跨表一致性问题。

### 3.4 迁移

`onUpgrade(oldVersion < 3)`：加列 + 把现有行的 `updated_at` 初始化为 `created_at`，`deleted=0`。老数据零丢失。

## 4. 同步协议设计

### 4.1 同步单元

以**物品记录**为同步单元（含其 moves 历史、照片引用），每单元携带 `updated_at`。家庭场景记录量小（通常 < 1000 条），物品级粒度协议最简单、冲突最清晰。

### 4.2 记录传输格式（JSON）

```json
{
  "id": 12,
  "name": "剪刀",
  "location": "客厅茶几抽屉",
  "photo": "photo_1725000000000.jpg",
  "created_at": 1724900000000,
  "updated_at": 1725000000000,
  "deleted": 0,
  "moves": [
    {"location": "卧室床头柜", "moved_at": 1724900000000},
    {"location": "客厅茶几抽屉", "moved_at": 1725000000000}
  ]
}
```

> 物品 `id` 为各设备本地自增，**不跨设备保证唯一**。协议中以 `(设备ID, 物品ID)` 二元组作为全局唯一键：每台设备首次同步时生成一个随机 `device_id`（UUID 短码），随同步交换。冲突时按 `updated_at` 裁决，胜利方的记录**整体覆盖**（含 id 重映射），失败方记录从本地删除/标记。

### 4.3 接口清单

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/health` | `{ok, app, version, device_name}` 探测与展示 |
| POST | `/api/sync/pull` | 拉取主机自 `since` 以来的变更 `{since, device_id} → {server_time, items[], locations[], photos_meta[]}` |
| POST | `/api/sync/push` | 推送客户端变更 `{device_id, items[], locations[]} → {accepted, conflicts[]}` |
| GET | `/photo/<filename>` | 照片**加密流**下载（AES-CTR，按需） |
| POST | `/api/handshake` | `{pin, device_id} → {ok, server_device_id}` 握手校验 |

- 传输：HTTP + JSON（UTF-8），客户端用 `HttpURLConnection`（零新依赖）
- 端口：默认 `8888`，设置页可改
- **幂等性**：所有接口以 `(device_id, id, updated_at)` 为键做合并，重复推送无害（断线重试安全）

### 4.4 同步流程（一次完整同步）

```
1. 客户端扫码/输 IP+端口+PIN → 握手（/api/handshake）
2. PULL：客户端 GET /api/sync/pull?since=本地上次同步时间
   → 拿到主机自该时间以来的所有变更（含 deleted=1 墓碑）
3. 本地合并（见 4.5），记录冲突
4. PUSH：客户端 POST /api/sync/push 把自己自上次同步以来的变更推给主机
   → 主机同样合并，返回冲突清单
5. 照片按需下载：对合并后仍缺文件且被记录引用的照片，逐个 GET /photo/<name>
6. 双方更新 last_sync_at = 本机当前时间（以主机时钟为准，见 4.5）
```

### 4.5 冲突处理策略（last-write-wins，LWW）

| 场景 | 处理 |
|---|---|
| 两台都改同一物品 | `updated_at` 大者胜，整体覆盖；失败方删除本地该条 |
| 一删一改 | **删除胜**（deleted=1 优先），避免"复活" |
| 同一时刻（相等时间戳） | 主机设备 ID 字典序大者胜（确定性，避免震荡） |
| locations 重名 | 名称相同视为同一条，`updated_at` 大者胜 |

- 同步完成后 UI 提示：`本次同步 N 条记录，M 条冲突（按较新的修改生效）`
- **时钟偏差风险**：家庭设备时钟可能不准。缓解：合并后统一按**主机时钟**重写 `updated_at`（主机为权威时间）；若两台都当主机（轮流），偏差仅影响冲突裁决边界，家庭场景可接受（文档注明，不引入 NTP）
- 照片文件名带毫秒时间戳，天然唯一，不冲突

### 4.6 照片传输

- 记录里的 `photo` 只传**文件名**，不内嵌 base64（省流量）
- `photos_meta` 返回主机照片清单（文件名+大小），客户端对比本地后只下载缺失的
- 下载失败不阻塞同步：记录先合并，照片标记"待下载"，下次同步自动重试

### 4.7 安全（家庭局域网级别）

- **PIN 握手**：主机随机生成 4 位 PIN 显示在屏幕上；二维码内容含 PIN（`findit://sync?host=...&port=8888&pin=1234`），扫码连接免输；手动连接需输 PIN——防止误连隔壁设备
- **应用层加密（v2.1 起）**：`/api/*` 请求/响应与 `/photo/*` 照片流**全部加密传输**：
  - 密钥 = `PBKDF2-SHA256(PIN, 固定盐, 65536 轮)` → AES-256，仅存内存（按 PIN 缓存）
  - JSON 接口：`AES-256-GCM` 信封 `{v:1, c:base64(iv‖密文‖tag)}`，防篡改 + 认证
  - 照片：`AES-256-CTR` 流加密（文件名派生确定性 IV），密文与明文等长，仍可流式传输
  - 即明文 HTTP 通道上不再裸传任何记录/照片数据；PIN 同时是**接入凭证**与**密钥种子**
- **边界说明**：4 位 PIN 熵约 1 万，本方案防「旁观窃听明文」，不防持有 PIN 者或对设备的物理访问；在线暴力破解需逐次尝试且每次都要过 65536 轮 PBKDF2，代价可观
- **版本兼容**：v2.1 与 v2.0 的同步协议不互通（加密封装变化），两台设备需同时升级到 v2.1+
- 主机模式默认只在**设置页显式开启**时运行，App 不常驻监听（省电/安全）；开启后由**前台服务**托管，退出 App 不中断（见 §5）

## 5. 客户端 UI 设计

设置页新增「多设备同步」区块（主界面零改动）：

```
多设备同步
┌─────────────────────────────────┐
│ 本机设备名：客厅手机（可改）          │
│                                   │
│ [ 开启主机模式 ]  ←→ 状态：已开启    │
│   地址：http://192.168.1.5:8888   │
│   [二维码]  PIN: 1234             │
│                                   │
│ [ 连接主机 ]（扫码 / 手动输入）      │
│   上次同步：10:23 · 共 3 条 · 0 冲突 │
│ [ 立即同步 ]                       │
└─────────────────────────────────┘
```

- **主机模式**：开关 + 显示 IP:端口 + 二维码 + PIN；开启后由**前台服务**持有（`SyncHostService`，类型 `specialUse` 无 6 小时时限），通知栏常驻 + 「停止主机」操作按钮；App 退后台/被划掉后主机继续运行，重启设备后需重新开启
- **客户端模式**：扫码（复用 zxing）或手动输入 IP:端口 + PIN
- **状态区**：上次同步时间、本次同步条数、冲突数、连接状态
- **同步时机**：手动「立即同步」为主；客户端连接成功后，App 在前台时每 30 秒静默探测一次主机在线并自动同步（失败静默，不打扰）

## 6. 容错与数据安全

| 场景 | 行为 |
|---|---|
| 主机离线 / 断网 | 同步静默失败，本地继续正常使用（本地优先架构） |
| 同步中途断连 | 接口幂等，重试安全，不会产生半同步状态 |
| 批量合并失败 | 单批合并包在**一个 SQLite 事务**里，失败整体回滚 |
| 主机重启 | 重新扫码/连接即可，数据在本地无丢失 |
| 卸载一侧设备 | 另一侧数据完好；建议卸载前先同步一次 |
| PIN 错误 | 拒绝握手，提示重新输入 |

## 7. 技术选型

| 项 | 选型 | 理由 |
|---|---|---|
| 内置 HTTP 服务 | **NanoHTTPD**（单 jar，Maven Central） | Android 最成熟的嵌入式服务器，省去手写 HTTP 解析；备选：原生 ServerSocket（零依赖但代码多） |
| 二维码生成 | `com.google.zxing:core`（QRCodeWriter） | 扫码侧已熟悉 zxing；生成侧用同一库，无学习成本 |
| 二维码扫描 | 现有 `zxing-android-embedded` | 已引入 |
| 同步客户端 | `HttpURLConnection` + org.json | 零新依赖 |
| 冲突/合并 | 纯 Kotlin 内存合并 + SQLite 事务 | 无第三方依赖 |

新增依赖仅：`org.nanohttpd:nanohttpd` + `com.google.zxing:core`（均可从 Maven Central 下载，CI 与本地构建一致）。

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| 路由器开启 AP 隔离（设备互访被拦） | 文档注明需关闭 AP 隔离/使用同一正常 WiFi |
| 手机后台杀进程（主机被关） | **已解决（v2.1）**：前台服务托管（specialUse 类型），通知栏常驻 + 一键停止；仅系统重启/手动停止会关闭 |
| 时钟偏差影响冲突裁决 | 合并后按主机时钟归一化 updated_at；家庭场景可接受 |
| 内网 IP 变化（二维码失效） | 每次开启主机模式重新生成二维码；手动连接可改 IP |
| 数据量增长 | 增量同步 + 照片按需下载，千条记录毫秒级完成 |
| 删除墓碑清理导致「复活」 | **已解决（v2.1）**：不再自动清理 30 天前墓碑——清理会让离线设备把已删记录重新推回。家庭规模墓碑体积可忽略（每年几 KB），永久保留 |
| 明文 HTTP 被旁观窃听 | **已解决（v2.1）**：PIN 派生密钥对 JSON 接口与照片做应用层加密（见 §4.7） |
